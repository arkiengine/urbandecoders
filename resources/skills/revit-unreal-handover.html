Quick reference

How to run it.

What a real-time engine actually needs, checked before anyone exports: placement, identity, polygon budget, materials, hygiene. Modifies no model, runs no export. Makes the first export the real one.

Run it

Attach the model export, a schedule export or a model summary:

Check this Revit model before we export to Unreal for the operational twin.
Our scene jitters when the camera moves. Is it the coordinates?
Where's the polygon budget actually going? We can't cut everything.
What do we strip before export, and what has to be fixed in Revit first?

Say the engine, the target hardware, and whether live data will bind to the model. Without those the report can rank, but it cannot advise.

The four problems that account for nearly all of it

  1. Coordinate magnitude. True survey coordinates in a single-precision engine means jitter, shimmer and bad snapping. It reads as an engine bug. It is a placement decision made weeks earlier in the authoring model.
  2. Nothing to bind to. Elements arriving as Wall_412837 with no type, no level, no classification and no persistent id can be looked at but not operated. This is the difference between a visualisation and a twin.
  3. Weight in the wrong places. Ironmongery, pipe fittings and light fittings routinely outweigh the whole envelope. With no per-category census, everything gets decimated and the building looks worse for no gain.
  4. Materials that cannot be authored. Unassigned, over-shared, or no usable UVs — each is engine-side rework, cheaper to prevent than to fix.

What it will not do — by design

  • Modify the model. No purging, decimating, renaming or re-origining. It prescribes; the author performs it in their tool.
  • Run the export, or write engine-side code, Blueprints, materials or import scripts.
  • State a polygon limit, draw-call budget or performance threshold from memory. Budgets depend on hardware, scene, lighting and frame-rate target. Give it the budget, or it ranks counts without a threshold.
  • Promise a frame rate or predict performance.
  • Choose the placement strategy. It states the options and the trade-offs.
  • Let an [estimated] triangle count reach a decision without its assumption attached.
  • Treat a visualisation-ready model as twin-ready. The identity section is where that distinction lives, and it is never softened.

Work the output

  1. Settle placement first, and record the offset somewhere that travels with the model. An undocumented offset is what breaks the twin's relationship to GIS six months later.
  2. Read the identity section before committing to a twin. If nothing stable survives the export, fix it in the authoring model — rebuilding a matching layer engine-side costs far more.
  3. Cut from the top of the ranked census, not across the board. That is the whole reason for ranking.
  4. Take the instancing list seriously; it is the cheapest large win available and it is usually left on the table.
  5. Fix hygiene before export. Coincident faces z-fight in the engine and get reported as a rendering problem by someone who will never find the cause.
  6. Re-run before each major re-export. Models gain weight quietly, and the category that was fine last month is often the new top consumer.

Remember: the export is the easy part. Everything that makes the result usable was decided in the authoring model, and this check is how you find out before the scene is already slow.

Triggering

When Claude reaches for it.

This is the description Claude itself reads to decide whether the skill applies. It is worth knowing, because it tells you exactly how to phrase the ask — and what the skill will decline.

revit-unreal-handover

Check a BIM model and its export settings against what a real-time engine actually needs before anyone exports: origin and coordinate magnitude, units, level and category structure, naming and instance identity for runtime data binding, material and UV readiness, tessellation and polygon budget by category, duplicate and degenerate geometry, and what must be decimated, instanced or excluded. Returns a readiness report and an export checklist; it modifies no model and runs no export. Use this WHENEVER someone asks to "prep this model for Unreal", "why does our model jitter in the engine", "get this ready for Datasmith", "check the model before we export to the twin", "how heavy is this going to be", "what do we strip before export", or is moving Revit, Rhino or IFC geometry into a real-time or web viewer. Do NOT use it to perform the export, decimate or edit geometry, write engine-side code or Blueprints, audit general model health (revit-model-audit), or reconcile multi-dataset georeferencing (crs-georeference-check).
